# RollBoard Studio · 滚榜工作台

从**本地部署的 DOMjudge / HOJ** 拉取指定比赛的榜单数据，重建成「封榜瞬间榜单 + 封榜后待揭示提交」，预处理为一份与 OJ 完全解耦的统一数据文件（`.rboard.json`），然后用这份文件做现场滚榜。

> *ICPC-style scoreboard resolver / unfreeze tool — pull contest data from a self-hosted DOMjudge or HOJ, precompute the reveal, then replay it offline.*

```
OJ 本地部署  ──HTTP──▶  适配器（DOMjudge / HOJ / 导入）
                            │  重建封榜状态 + 交叉校验
                            ▼
                   data/contests/*.rboard.json
                            │  纯前端引擎（无需 OJ、无需联网）
                            ▼
                  全屏滚榜大屏 board.html
```

**零第三方依赖**，Node ≥ 18 即可运行；数据文件可拷到任意电脑离线滚榜。

## 快速开始

仓库：`https://github.com/TechieBreeze/rollboard`

```bash
git clone https://github.com/TechieBreeze/rollboard.git
cd rollboard
npm start          # 零第三方依赖，不需要 npm install
# 工作台     http://127.0.0.1:5173/
# 配置中心   http://127.0.0.1:5173/setup.html
# 滚榜大屏   http://127.0.0.1:5173/board.html
```

启动后终端会显示带 `#admin=...` 的管理链接与管理口令。使用该链接进入工作台即可登录；直接打开工作台时也可输入管理口令。登录后同一浏览器可打开配置中心，会话最长 12 小时，重启服务后失效。可通过环境变量 `ROLLBOARD_ADMIN_TOKEN` 指定固定口令（至少 16 个字符）；不设置则每次启动随机生成。只把 `/board.html` 链接分享给观众，观看无需登录。

需要 Node ≥ 18（服务端用到内置 `fetch`；UI 回归脚本用 Node 22 的全局 `WebSocket` 驱动 Chrome）。首次登录工作台会自动生成一场演示比赛，点「打开滚榜大屏」即可立即体验。

`data/` 目录、默认配置和演示数据都在首次运行时自动创建，**不入库** —— 每台机器各自维护自己的数据源与比赛文件。

需要让同一局域网的其他机器访问大屏时：

```bash
HOST=0.0.0.0 PORT=8080 npm start
```

## 三个页面的分工

| 页面 | 用途 |
| --- | --- |
| `/` 工作台 | 看数据文件、临时拉取一场比赛、导入 JSON、生成演示数据 |
| `/setup.html` 配置中心 | **所有可调项集中在这里**：数据源、拉取默认值、奖牌名额、播放默认值、快捷键键位 |
| `/board.html` 大屏 | 现场滚榜。控制条只留播放控制与设置入口，其余收进设置抽屉 |

工作台优先显示比赛数据文件，支持按名称 / ID 搜索和按来源筛选；下方可拉取比赛、选择或拖入 JSON 文件。配置页的保存栏在窄屏下也保持可见，修改字段后会显示未保存状态。管理台支持页面内登录、退出、键盘焦点与深浅主题；这些样式独立于滚榜大屏。

配置保存在 `data/config.json`，大屏与工作台读取同一份。

## 1. 连接 DOMjudge

在**配置中心 `/setup.html` → 「数据源」**新增，类型选 `DOMjudge`，Base URL 填 **Web 服务根地址**，例如 `http://127.0.0.1:8080`（工具会自动探测 `/api/v4` 与 `/api` 两套前缀）。

| 项目 | 说明 |
| --- | --- |
| 比赛 ID | DOMjudge 的 `cid`，如 `3` / `nwerc18`；也可点「列表」读取 |
| 凭据 | 拉取 `submissions`、`judgements` 需要 **jury 或 admin** 权限的 HTTP Basic 账号密码 |
| 封榜时刻 | 默认读取 `scoreboard_freeze_duration`；若比赛没配置封榜，可在「覆盖封榜时刻」里手动填「结束前 N 分钟」 |
| 隐藏队伍 | 默认剔除 `hidden` 队伍，可勾选包含 |
| 打星队伍 | 分组名含 `star / 打星 / 观众 / guest / unofficial` 的队伍自动标记为打星 |

使用的端点（全部由服务端请求，不受浏览器 CORS 限制）：

```
GET /api/v4/contests/{cid}                  比赛信息与封榜配置
GET /api/v4/contests/{cid}/problems         题目与颜色
GET /api/v4/contests/{cid}/teams            队伍
GET /api/v4/contests/{cid}/organizations    单位
GET /api/v4/contests/{cid}/groups           分组
GET /api/v4/contests/{cid}/submissions      提交（需 jury/admin）
GET /api/v4/contests/{cid}/judgements       判定（需 jury/admin）
GET /api/v4/contests/{cid}/judgement-types  判定类型
GET /api/v4/contests/{cid}/scoreboard       官方榜单（交叉校验）
```

预处理逻辑：用 `contest_time` / `time` 把提交换算成相对开赛秒数，按交题顺序将封榜前提交的最终判定重放成 `frozen`；判题完成时间不参与封榜划分，封榜前交的题即使封榜后才判完，也计入初始榜。封榜后的提交、以及拉取时仍无判定结果的提交进入 `submissions` 待揭示列表。最后用 jury 榜单核对重建出的**最终通过题数与总罚时**，结果写进 `meta.validation`，在工作台可见「一致 / 有差异」。

> 拉取动作本身在**工作台 `/`** 的「快速拉取」区发起：选数据源 → 填比赛 ID / 账号密码 → 点拉取。配置中心只负责**存**这些选项（数据源、账号、奖牌线、封榜默认值），工作台负责**用**它们。

## 2. 连接 HOJ (Hcode Online Judge)

在**配置中心 `/setup.html` → 「数据源」**新增，类型选 `HOJ`，Base URL 填**后端 API 根地址**（工具会尝试 `{base}/api/...` 与 `{base}/...`）。直接使用 HOJ 自带的匿名滚榜接口 `@AnonApi`，**无需登录**：

```
GET /api/get-contest-scroll-board-info?cid={cid}
GET /api/get-contest-scroll-board-submission?cid={cid}&removeStar=false
```

- `info` 提供 `startTime`、`sealRankTime`（封榜时间）、`balloonColor`（题号与颜色）、`rankShowName`（榜单显示名）、`starUserList`（打星用户名）。
- `submission` 提供 `submitId / uid / displayId / status / submitTime` 及冗余的队伍信息；`status` 按官方 `scrollboard.js` 的 `statusMap` 转换（`0→AC`、`-1→WA`、`-2→CE`、`5/6/7/9→PENDING` 等）。
- HOJ 滚榜接口**不返回比赛结束时间**，因此 `durationSec` 由最晚提交时间向上取整推断，仅用于展示，不影响滚榜。
- HOJ 手动填写「结束前 N 分钟封榜」时，必须同时在配置中心填写「实际比赛时长」（例如 300 分钟），防止把推断时长用于封榜划分；不覆盖时仍采用 HOJ 自带封榜时刻。
- HOJ 的比赛列表接口各版本差异较大，若「列表」为空，直接手填 CID 并用「测试连接」验证即可。

## 3. 导入已有 JSON / 演示数据

工作台「导入 / 演示」支持拖拽或粘贴，自动识别：

- 已处理好的 `rollboard/1` 文件；
- DOMjudge 端点响应集合：`{ contest, problems, teams, submissions, judgements, judgementTypes?, organizations?, groups?, scoreboard? }`；
- HOJ 响应集合：`{ info, submissions }`（也可直接贴 HOJ 接口的 `data` 内容）。

「生成演示比赛」会产出 13 题 / 72 队 / 441 条封榜后提交的确定性样例（队名来自 30 所学校、全部唯一；最后三支打星队与部分难题只在封榜后被攻破，因此包含一血展示），共 **739 个原子步骤**（一队一题粒度）：298 次高亮 + 277 次揭晓 + 21 次荣誉 + 72 次空行 + 71 次焦点移动，方便调音、调动画、调奖牌线。

切到「逐条提交」粒度则是 **1067 步**：462 次高亮 + 441 次揭晓 + 21 次荣誉 + 72 次空行 + 71 次焦点移动——一条提交一次揭晓，粒度更细。

规模已调到接近真实比赛（72 队 × 13 题 = 936 个格子），这样才能暴露**渲染性能问题**：小数据下流畅的成绩，放到大屏真实数据上就会卡。

## 4. 现场滚榜

大屏地址 `board.html?id=<文件ID>`，也可在页顶下拉框切换文件。

### 纯净模式（现场用这个）

按 **`P`** 进入纯净模式：**顶栏、状态条、控制条全部退场，屏幕上只有榜单**，表格占满视口，行高和字号同步放大。

- 鼠标指针自动隐藏，移动鼠标时短暂出现（方便操作者确认位置，不打扰观众）
- 任何操作（调速、跳转）都会在屏幕下方弹一个提示浮层，1.8 秒后自动淡出
- 再按 `P` 或 `Esc` 退出

| 键 | 作用 | 键 | 作用 |
| --- | --- | --- | --- |
| `空格` | 播放 / 暂停 | `Ctrl + →` | 跳到下一个揭晓 |
| `→` | 下一步 | `Ctrl + ←` | 跳到上一个揭晓 |
| `←` | 上一步 | `Alt + →` | 跳到下一个荣誉时刻 |

### 播放设置

控制条只保留播放控制与几个入口，完整选项在 **设置抽屉**（`S` 或 ⚙ 按钮）里，**播放过程中也能随时打开调整**：

| 选项 | 说明 |
| --- | --- |
| 揭晓粒度 | 「一队一题」（传统）或「逐条提交」（更细）；切换会重建步骤 |
| 播放速度 | 0.5× / 1× / 2× / 4× / 8× / **极速**（默认 1× = 1000ms 基准，739 步约 8.4 分钟；极速约 40 秒） |
| 行移动动画 | 默认开启；时长随播放速度自适应（高速档自动缩短），也可手动关掉 |
| 打星队计入排名 | 默认打星队不占正式名次，排在最后 |
| 音效 | AC / 未通过 / 荣誉有不同提示音 |
| 焦点样式 | 「反色」对比最强（默认）/「主色高亮」更柔和 |

### 主题（深色 / 浅色）

两套主题共用同一份 DOM 结构与同一份样式表，颜色全部走 CSS 变量，实现在 `public/css/theme.css`：

| 令牌组 | 作用范围 |
| --- | --- |
| `--rb-*` | 滚榜大屏：背景、条纹行、表头、题目胶囊、焦点行、序幕页、全屏奖项页、终榜卡片、控制条 |
| `--ui-*` | 管理台：背景、面板、输入框、侧边栏、代码块、表格、标签、弹窗、Toast |

- 切换：大屏控制条 `◐` 按钮、管理台右上角与侧边栏底部的按钮，或按 `T`。
- 持久化：写入 `localStorage['rollboard.theme']`，管理台与大屏共享同一份选择。
- 默认：未设置过则跟随系统的 `prefers-color-scheme`，系统为浅色时大屏默认浅色，否则深色。
- 焦点行在两套主题下都是「整行反色」，只是反的方向相反：深色主题是亮底深字，浅色主题是深底浅字。
- 主题脚本内联在 `<head>` 中先于样式表执行，首屏不会闪白/闪黑。

### 大屏视觉（ICPC Resolver 风格）

参照 ICPC Tools Resolver 的界面语言重做：

- **纯黑底 + 条纹行**，无网格线；队名大字号并带圆形队徽，`SOLVED / TIME` 置于最右。
- **题目是宽扁胶囊**：深灰 = 未尝试，琥珀黄 `?N` = 待揭晓，绿 `+N/mm` = 通过，红 `-N` = 失败，`FB` 角标 = 一血。
- **焦点行整行反色**（亮底深字 + 左侧金色竖条），这是 Resolver 的标志性高亮；`select` 步骤再给目标格子加白色脉冲描边。
- **开场序幕页**显示比赛名、队伍/题目/封榜/奖牌信息；**一血与金银铜奖切换为全屏 citation 页**（队徽、奖项名、队名、题词、最终名次），停留更久。
- 名次上升时整行以 FLIP 动画上移；终榜展示冠军与奖牌名单。

自动播放按步骤类型控制节奏：`select` / `empty` / `move` 较短，`reveal` 正常，荣誉展示停留更久；间隔下限 40ms，极速档 739 步约 40 秒跑完。

### 动效

动效全部用 **Web Animations API** 播放，不依赖 CSS class 切换，因此**不会触发强制回流**——这是性能的关键（之前用 `void el.offsetWidth` 重播动画会让每步从 5.7ms 涨到 27ms）。

| 动效 | 触发时机 | 效果 |
| --- | --- | --- |
| 焦点光扫 | 焦点换到新队伍时 | 一道光带扫过该行，提示注意力转移 |
| 名次弹跳 | 某队名次发生变化时 | 数字上下弹一下 |
| 通过数闪光 | 某队通过数增加时 | 数字闪一下金色 |
| 待揭晓呼吸 | **慢速档**下当前焦点行的待揭晓格子 | 轻微明暗呼吸，暗示"这里还有东西没揭晓" |

#### 动效预算：按步进间隔自适应

高速档「一闪一闪」有两个根因，缺一不可：

**① 动画时长超过步进间隔** —— 一个 620ms 的揭晓闪光放在 40ms 一步的高速档里，每步都只播到第 0 帧就被下一步打断，视觉上就是持续频闪。

**② 动画被「取消后重开」** —— 这个更隐蔽。名次数字 `rank-num` **每一个 reveal 步都会被 pulse 一次**（一次排名变动会让下方所有队伍的名次一起变），而 `pulse()` 原本的做法是「无条件 cancel 上一个动画再重开」。于是它的动画被反复从中间截断、重来——实测 120ms 档 39 次、60ms 档 30 次动画在 **68%~90% 进度处被砍掉**。人眼看到的正是这个：动画每次都「跳回起点重新弹」= 闪。

现在的做法：

- **不打断**：同一种动效还在**可见地**播放（进度 < 85%）时，跳过本次 pulse，让它自然播完。动画只是叠在数值之上的装饰——格子状态、名次数字都是**先写文本**，数值变化不会丢。（`isPlaying()` 会区分动效种类：select 的呼吸没播完，不会吞掉 reveal 的揭晓闪光。）
- **时长自适应**：时长从**真实步进间隔**推导（`stepInterval()` 是播放节奏的唯一真源，动效预算与定时器共用它），取 `min(标称时长, 间隔 × 比例, 间隔 × 0.5)`。
  - 上限取 **50%** 而不是「略小于」：动画在 `render()` 里创建，但 `startTime` 要等到**下一个浏览器帧**才赋值（60Hz 下约 16.7ms 后），真正可用的是「间隔 − 一帧」。按 62% 算时，60ms 档的动画会在 90% 进度处被砍掉尾巴。
- **幅度收敛**：激进度 `intensity()` 随间隔收紧——位移、缩放、**亮度**都按比例压小。`brightness(1.55)` 的白闪是频闪的主要光源，高速档会拉回接近 1.0。
- **过渡时长**：格子底色、行的背景/前景色渐变由 CSS 变量 `--rb-fx-t` 驱动，同样随间隔收紧，避免「啪一下跳变」。
- **持续性动效**：光扫在间隔 < 200ms 时跳过；呼吸只在慢速档（`body.fx-calm`）开启——焦点每 40ms 就换一行时，呼吸动画每步重启，格子会一直停在关键帧 0%，那正是一格一格地闪。
- **极高速档**（间隔 < 70ms，`body.fx-off`）直接关闭所有渐变过渡：40ms 的渐变人眼看不出，只会在步与步之间产生微弱的跳变感，不如直接切换来得干脆。

实测（4 个档位 × 49 步，拦截 `Animation.prototype.cancel`）：

| 档位 | 步进间隔 | 动画时长上限 | 可见播放中被取消 | 揭晓闪光触发率 |
| --- | --- | --- | --- | --- |
| 1× (1000ms) | 1000ms | 500ms | **0** | 24/24 |
| 4× (250ms) | 250ms | 125ms | **0** | 24/24 |
| 8× (120ms) | 120ms | 60ms | **0** | 24/24 |
| 极速 (60ms) | 40～60ms | 30ms | **0** | 24/24 |

「可见播放中被取消 = 0」与「揭晓闪光 100% 触发」要**同时**成立才算修好——只满足前者就变成「不放动画」，把滚榜最关键的那一下也丢了。

真实播放时帧间隔中位数 16.7ms（60fps 持续），与页面空闲时的基线持平。739 步全量同步渲染的中位耗时 **0.4ms**（p90 3.1ms / p99 6.8ms），极速档每步间隔 40ms，余量非常充足。

> **回归保障**：`tests/ui-regression.js` 会逐档位检查「动画在可见播放中不得被取消」以及「每个 reveal / select 步都必须真的触发对应动效」。`npm run test:fx` 与 `npm run test:frames` 是可独立运行的专项诊断。

#### 「跳步」：画面滞后于逻辑步进

高速档下曾出现「跳步」——不是动画被吃掉，而是**画面卡住，隔一段时间才刷一次，刷出来时已经过了好几步**。声音正常恰好说明定时器时钟是准的，问题只出在渲染侧。

**根因：强制同步 layout。** 焦点行锚定原本靠读 `offsetTop` / `offsetHeight` / `clientHeight` 计算滚动位置，并在 DOM 刚被改写（DOM 脏）时立刻写 `scrollTop`。这两件事各自都会让浏览器**当场把整张表重排一遍**——72 行 × 13 列 = 936 个格子，一次完整 layout 实测约 43ms。而极速档步进间隔只有 40ms，单步渲染耗时本身就超过间隔，主线程被 layout 占满，画面自然只能「攒几步刷一次」。

分段实测（60 步）：

| 渲染内容 | 耗时 |
| --- | --- |
| 重排行 + 改格子，**不写** `scrollTop` | 1ms |
| 重排行 + 改格子 + **写** `scrollTop` | 226ms |

差值全在那个同步 layout 上。CPU Profiler 也印证了这点：`anchorFocusRow` 一度占 **91.9%** 的 self time。

**三层修法：**

1. **算术定位**：行高固定（等高行），焦点行在表内的位置直接算出来 —— `表头高 + (槽位名次 − 1) × 行高`，**零布局读取**。行高、表头高、视口高全部缓存，`resize` / `fullscreenchange` / `visualViewport.resize` 时才重新测量。
2. **滚动写入延后到 `requestAnimationFrame`**：`render()` 里只**记下**目标滚动位置，真正的 `scrollTop` 写入放到下一帧的 rAF 回调 —— 那时浏览器已经把 layout 算完了，写入几乎免费（实测 0.17ms）。
3. **重排改为逐行定位**：从后往前把第 i 行插到第 i+1 行之前，并用 `previousSibling` 比较跳过「已经在位」的行。典型的一次名次变动只需 1～3 次 DOM 写，而不是原先的 ~30 次。

**效果**（72 队 × 13 题）：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 单步渲染 p50 | 24.4ms | **0.4ms** |
| 单步渲染 p90 | 52.4ms | **3.1ms** |
| 单步渲染 p99 | 87.7ms | **6.8ms** |
| CPU 采样总数 | 11439 | **773**（−93%） |

画面更新节奏（用 `MutationObserver` 直接量「格子 DOM 真正被改写」的时刻）：

| 档位 | 修复前画面间隔 | 修复后画面间隔 | 每次画面跨过的步数 |
| --- | --- | --- | --- |
| 1× (1000ms) | 1093ms | 1006ms | 1 |
| 4× (250ms) | 200ms | 137ms | 1 |
| 8× (120ms) | 139ms | 111ms | 1 |
| 极速 (60ms) | 124ms | 100ms | 1 |

修复后所有档位的「一次画面更新跨过多步」比例都是 **0**。

> **回归保障**：`tests/ui-regression.js` 有两道专门的防线 —— ① 单步渲染预算（p50 ≤ 30ms）；② 画面滞后（跨步比例 ≤ 5%，且画面间隔中位数 ≤ 步进间隔 × 2.5）。这两条一旦被打破，测试会直接失败。

**引擎规则（焦点行）**：焦点从**最后一名**开始，停驻在「名次位置」上，不跟着队伍走。

1. 焦点行**还有未揭晓提交** → 先高亮最靠前的待揭晓格子（`select`，不改榜单），**下一步**才揭晓它（`reveal`，按题号顺序）。
   - **发生排名变动** → 该行向上移动，焦点**仍停在原位置**，由被挤下来的下一支队伍补位（绝不跟随上升的队伍向上）；
   - 没有变动 → 继续对同一队伍的下一题重复「先高亮、再揭晓」。
2. 焦点行**已无未揭晓提交** → 依次检查「一血」「获奖」展示项，有则先高亮准备、再展示（`ceremony`，不改榜单）。
3. 都没有 → 先输出一个 `empty` 步骤（**不跳过**这支队伍），**下一步**才用 `move` 把焦点上移一行。
4. 焦点扫过榜首即结束，此时所有提交揭晓完毕、所有一血与奖牌均已展示。

**步骤是加载时一次性预计算好的**：每个 step 都带一份完整榜单帧 `frame`（state / ranks / 焦点位置），相邻帧通过结构共享复用未变化的行与格子。播放时直接取 `step.frame`，**不重放提交、不重算排名**；DOM 也只增量更新引用变化的那个格子，只在排名顺序真正变化的那一段做行位移。

### 视角：焦点行锚定在屏幕下方

焦点行不是「滚到能看见就行」，而是**稳定停在视口下方**（距底部约 22% 处，锚点为视口高度的 78%）。

因为焦点停在**名次槽位**上（排名变动只换队伍、不换槽位），所以焦点上移一行时视口跟着上移一行，**焦点行在屏幕上原地不动**——观众的视线不用追着焦点跑，揭晓时镜头也不会晃动。

唯一的例外是**顶部空间不够**：当焦点已经接近榜首、表格滚到最顶也没法把焦点行压到锚点时，退化为最小滚动，让焦点行随名次槽位自然升到视口上部（实测第 8 名起开始出现，第 1 名时位于视口 21% 处）。

> 滚榜过程中**鼠标滚轮不会滚动榜单**——纵向位置由焦点锚定独占控制，操作者一不小心滚一下就会把画面带偏。这里不用 CSS `overflow:hidden`（那会破坏 sticky 表头与程序化滚动），而是拦截 `wheel` 事件；程序化写 `scrollTop` 不受影响。`Ctrl + 滚轮` 放行，方便调试时缩放查看。

## 5. 快捷键

配置中心（`/setup.html`）里可以改所有键位。

**录制方式**：点击键位输入框 → 直接按下想要的组合 → 自动写入。`Esc` 取消录制。

键位用 `KeyboardEvent.code` 存储（物理键位），**与输入法无关**——中文输入法下打字也不会错位。

支持的组合：

| 类型 | 例子 |
| --- | --- |
| 单键 | `Space` `Period` `Comma` `KeyP` `ArrowRight` |
| 修饰键组合 | `Ctrl+ArrowRight` `Alt+ArrowDown` `Shift+Period` |
| 数字键 | `Digit1` ~ `Digit9` |
| 小键盘 | `Numpad1` ~ `Numpad9` |

左右侧的修饰键自动归一（`ControlLeft` / `ControlRight` 都算 `Ctrl`），所以不存在"左手按 Ctrl 和右手按 Ctrl 行为不同"的问题。

## 统一数据格式 `rollboard/1`

```json
{
  "schema": "rollboard/1",
  "meta": {
    "id": "2026-final", "title": "2026 校赛决赛",
    "sourceType": "domjudge", "contestId": "3",
    "startTime": "…", "freezeTime": "…", "endTime": "…",
    "durationSec": 18000, "freezeSec": 14400, "penaltyMin": 20,
    "medals": { "gold": 4, "silver": 6, "bronze": 8 },
    "stats": {}, "validation": {}
  },
  "problems": [{ "id": "A", "label": "A", "name": "签到", "color": "#ef4444" }],
  "teams": [{ "id": "1", "name": "队名", "org": "学校", "starred": false }],
  "frozen": { "1": { "A": { "attempts": 1, "solved": true, "solveSec": 1240 } } },
  "submissions": [
    { "id": "s812", "teamId": "1", "problemId": "F", "timeSec": 15230,
      "verdict": "AC", "penalty": true, "pendingAtFreeze": false }
  ]
}
```

- `frozen[team][problem].attempts`：封榜前、AC 之前的计罚错误提交数。
- `submissions`：**只放待揭示的提交**（封榜后提交 + 拉取时仍无判定结果的提交），按交题时间排序；`penalty=false` 的结果（CE/PE/SE/PENDING）不计 20 分钟罚时。旧文件若将已公开 AC 之前的罚时失败放在此列表，引擎会在加载时补齐这些罚时，避免滚榜过程中名次向下倒退；更早的 AC 或同秒先后顺序不能仅靠聚合成绩可靠恢复，应重新拉取原始数据。
- 文件自包含，不依赖 OJ、不依赖数据库，可随意复制归档。

## 数据与隐私

- 所有文件保存在 `data/`：`sources.json`（数据源配置）、`config.json`（全局配置）、`contests/*.rboard.json`（统一文件）、`raw/*.raw.json`（原始响应快照，便于复盘）。
- **密码从不落盘**：`config.json` 里不含任何密码字段，服务端在写盘前会主动剔除。密码只存在浏览器 `sessionStorage`（当前标签页会话），关掉标签页即失效；提交请求时由前端直接传给服务端，用完即走。
- `sources.json` 只保存用户名与地址。
- 服务默认只监听 `127.0.0.1`；对外展示时再显式设置 `HOST=0.0.0.0`。
- 管理 API（包括配置、数据源、原始快照、拉取与所有写入）要求管理口令或已登录会话；大屏使用独立的只读播放配置接口。浏览器会话通过 HttpOnly / SameSite=Strict Cookie 保存，不将管理口令写入 localStorage 或配置文件。命令行可使用 `Authorization: Bearer <管理口令>`。
- 跨来源重定向会清除自定义请求头和 Basic 凭据，拒绝 HTTPS 降级及跨来源转发请求体；同源重定向保持认证。
- 自签名 HTTPS 可在拉取表单勾选「允许自签名 HTTPS」。

## 测试与二次开发

```bash
npm test          # 引擎、适配器、导入时间单位、XSS、封榜边界、重定向凭据、管理权限及会话回归
npm run test:ui   # UI 全量回归（需先 npm start + 本机装有 Chrome）：主题、纯净模式、快捷键、配置页、动效、凭据检查
npm run test:admin # 管理界面交互与三种宽度的双主题截图；需要管理口令，使用模拟 OJ
npm run test:performance # 纯净模式真实播放：8× / 极速、两种粒度、4K 和 CPU 4× 降速，输出帧间隔与长任务
npm run test:fx        # 动效连续性专项：逐档位统计动画重播次数（应为 0）
npm run test:frames    # 播放流畅度专项：统计真实播放时的帧间隔与掉帧率
npm run mock      # 启动模拟 OJ（http://127.0.0.1:8791）
```

`npm run test:ui` 用 Chrome DevTools Protocol 驱动真实浏览器跑一遍关键交互，把结果打印成 JSON 并把截图写到 `data/ui-shots/`；没装 Chrome 或服务没启动时会自动跳过而不是报错。

UI 管理回归需要在测试进程设置与服务端相同的 `ROLLBOARD_ADMIN_TOKEN`；使用独立数据目录时，服务与测试同时设置同一个 `ROLLBOARD_DATA`，避免测试修改日常比赛配置。

`test:admin` 也需要以上两个环境变量，并会在隔离数据目录导入文件、添加本机模拟数据源及保存配置。上述浏览器脚本需 Node ≥ 22；可用 `ROLLBOARD_BASE` 指定服务地址、`CHROME_PATH` 指定浏览器路径。`test:performance` 不需要管理权限，但服务中须已有比赛文件。

高速滚榜优化包括：缓存滚动目标，避免每步读取 `scrollTop` 强制排版；极速档固定已禁用的过渡预算，不再反复改变根 CSS 变量；只写入发生变化的成绩、奖牌与名次。纯净模式的行位移动画使用实测行高。低性能设备仍可能出现绘制长帧，不能仅凭「没有跳步」判断不卡顿，应结合 rAF 帧间隔与长任务一起看。性能脚本中的 `dropRatio` 是超过 30ms 的帧间隔比例，不是硬件显示器的丢帧计数。

其中三项是**「跳步」专项防回归断言**，任何一条被打破都会让测试直接失败：

| 断言 | 判据 | 当前值 |
| --- | --- | --- |
| `fx.renderBudgetOk` | 单步渲染耗时 p50 ≤ 30ms（极速档一步只有 40ms） | p50 **0.3ms** |
| `fx.lagOk` | 画面更新跨步步数占比 ≤ 5%，且画面间隔中位数 ≤ 步进间隔 × 2.5 | 跨步比例 **0** |
| `fx.orderOk` | 每一步的 DOM 行顺序必须与预计算的 `frame.ranks` 完全一致 | 739 步 **0 处不符** |

`npm run test:fx` 与 `npm run test:frames` 是动效专项诊断，用于排查「高速档闪烁」这类问题：前者判断动画有没有被跨步重播（闪），后者判断播放过程有没有掉帧（卡）。两者同样零依赖、找不到 Chrome 就跳过。

模拟 OJ 同时实现两套接口，可当作一台真实本地 OJ 来联调：

- DOMjudge：地址 `http://127.0.0.1:8791`，比赛 ID `demo`，账号 `admin` / 密码 `demo123`
- HOJ：地址 `http://127.0.0.1:8791`，CID `42`（匿名）

新增其它 OJ 时，在 `lib/adapters/` 下实现 `listContests` 与 `fetchRaw` / `buildFromBundle` / `fetchContest`，并在 `lib/adapters/index.js` 注册即可；只要产出 `rollboard/1`，滚榜引擎和大屏无需改动。

## 常见问题

| 现象 | 处理 |
| --- | --- |
| DOMjudge 拉取 401 | 提交与判定接口需要 jury/admin 凭据，填 HTTP Basic 用户名密码 |
| 提示「未配置封榜时长」 | 在「覆盖封榜时刻」填结束前 N 分钟，滚榜才有悬念 |
| HOJ 列表为空 | 版本差异，直接填 CID，用「测试连接」验证 |
| 校验显示「有差异」 | 多半是封榜设置/重判导致，展开管理台的差异明细逐队核对；文件仍可正常滚榜 |
| 大屏题目列太挤 | 大屏会自动给出横向滚动；用 `F` 全屏或调高分辨率 |
